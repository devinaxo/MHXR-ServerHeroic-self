# Texture dump (v0282 -> v0286 GUI resource packs)

Generated by `tools-js/gui-tex-dump.cjs` + `tools-js/tex_batch_decode.py`.

```
dump/
├── tex/<pack>/<arc>/<entry>.tex   raw TEX, byte-identical to what the pack holds
├── png/<pack>/<arc>/<entry>.png   decoded RGBA4 (editable)
├── manifest.csv / manifest.json   one row per texture: pack, arc, entry, format,
│                                 type, WxH, size, sha256, path, status
└── summary.txt                    counts + the list of _jpn files
```

## Colour order (important)

`RGBA4` stores the four channels in one u16, **high nibble first**:

```
u16 = 0x R G B A      bits 15..12 = R, 11..8 = G, 7..4 = B, 3..0 = A
```

Reading the nibbles in the opposite order mirrors every hue and moves alpha into
the high nibble, which turns brown/gold UI art into saturated red and cyan. The
shapes still look right, so it is easy to mistake for a colour-grading problem —
check against `screenshots/menu.jpg` before trusting a decode. Every PNG in
`dump/png/` was regenerated 2026-10-08 with the corrected order, and 100 sampled
textures re-encode byte-for-byte identical to their `.tex`.

A consequence of 4 bits per channel: colours snap to multiples of 17
(0, 17, 34 ... 255). New art pasted in from elsewhere will band unless it is
authored to that palette; reusing the browns and golds already in an atlas
blends seamlessly.

`tex_android.py` and `tex_batch_decode.py` both implement this order in their
decode and encode paths, and must be changed together.

## Tiers (sort the manifest by these)

`tools-js/tex-tier-manifest.cjs` adds these columns to `manifest.csv` and
`manifest.json`. Re-run it after any change to the rules.

| column | values | use |
|---|---|---|
| `tier` | 1..4 | sort ascending for priority |
| `tier_label` | every screen / core loop / situational / event-banner | |
| `jpn` | 1 / 0 | 1 = filename ends `_jpn`, art with baked Japanese text |
| `decodable` | 1 / 0 | 1 = local decode possible (RGBA4/RGBA8/R5G6B5) |
| `category` | menu, common, quest, result, skill name, icon, banner, ... | group related art |

Tier rules (matched against the arc, then the entry path, first match wins):

- **T1 every screen** — `GUI_cmn`, `GUI_home_common`, `GUI_home_menu`, `GUI_home_equip`, `GUI_home_top`. Shared chrome, popups, the main menu, home screen.
- **T2 core loop** — quest / result / equipment arcs, plus `tex/skill_name` art (on screen constantly in equip and status menus).
- **T3 situational** — everything else under `GUI/`: town, guild, treasure, map, character, otomo, titles, icons.
- **T4 event / banner** — `ex_tex` banner and event art, `event_home/`, plus non-UI `stage/` and `effect/` assets.

Two filters worth keeping to hand:

```bash
# what you can edit right now, highest priority first
awk -F, 'NR==1 || ($2<=2 && $4==1 && $5==1 && $16!="duplicate")' dump/manifest.csv

# every _jpn texture still blocked pending PVRTC4 support
awk -F, 'NR==1 || ($4==1 && $5==0 && $16!="duplicate")' dump/manifest.csv
```

Counts: T1 120 textures (60 `_jpn`), T2 2104 (2010), T3 7607 (696), T4 781 (744).
The T1+T2 decodable worklist is **47 textures**; all of it sits in `GUI.00.fpk`.
Note that the largest single text category, `tex/skill_name` (1,966 `_jpn`
textures), is almost entirely PVRTC4 and therefore blocked until PVRTC decoding
is available.

## Editing and putting it back

```bash
python3 tools-js/tex_android.py encode dump/tex/<...>.tex edited.png out.tex
node tools-js/arc-edit.cjs <in.arc> <out.arc> <entry-substring> out.tex --replace-entry-only
node tools-js/fpk-replace.cjs GUI.00.fpk out.fpk GUI_home_top.arc <out.arc>
```

Keep the replacement the same byte size so `--replace-entry-only` preserves the
archive layout. This is verified working end to end.
